# Practice Agent Streaming Tools 生产报告

生成时间：2026-06-22

## Summary

这条分支把练习流程升级成了完整闭环：系统可以按轮次推荐题目、给出提示、批改作答，并基于本轮表现生成下一轮练习。

学生侧体验更连续了，能看到实时思考状态、耗时反馈、绿色正确标记，以及更简洁的轮次复盘。

同时，题目内容、导入链路和管理工具也更稳，尤其是在数学内容、结构化题目和批量审核场景下，展示和处理都更一致。

## 用户变化

- 练习从“给一组题”变成“推荐 - 作答 - 批改 - 复盘 - 下一轮”的连续流程。
- 每道题都可以单独请求提示，提示不会干扰主推荐上下文。
- 提交后会自动批改并生成简短反馈，再进入下一轮。
- 思考过程中会显示实时状态和耗时，结束后会显示本轮思考总时长。
- 正确题目的绿色标记更醒目，用户一眼就能看出结果。
- 复盘页只展示给学生看的简短反馈，下一轮目标不直接暴露。
- 数学题、题目摘要页、导入页、编辑页的内容渲染更一致，结构化内容更容易阅读。

## 产品影响

这条分支同时提升了三个层面：

1. 练习体验更连贯，不再是孤立的推荐动作。
2. 题目内容更清楚，数学和富文本展示更稳定。
3. 管理和导入流程更能承接复杂结构，不需要人工频繁修补。

## 技术总览

### Practice Agent 主流程

这次最核心的是一个流式推荐 agent，它负责把一次练习轮次串起来。

核心链路如下：

- `POST /api/practice/recommend` 负责生成推荐题目。
- `POST /api/practice/hint` 负责单题提示。
- `POST /api/practice/grade` 负责提交后的批改。
- `POST /api/practice/review` 负责轮次复盘和下一轮记忆更新。

agent 会维护压缩后的 `sessionMemory`、已完成题目、tag 上下文，并把过程事件流式传给前端。前端因此可以展示“系统正在做什么”，但不会暴露隐藏推理内容。

这条链路的关键设计是把上下文控制放在后端：

- 本轮的 tag 发现、候选题、最终选择都由 agent 自己管理。
- 前端只保存必要的轮次摘要、完成题号和少量记忆。
- 复盘后产生的下一轮方向会被压缩成简短记忆，而不是长历史。

### 工具与上下文管理

推荐环节使用的是一组很小的工具：

- `browse_taxonomy_batch` 用于找 tag
- `practice_search_batch` 用于找候选题
- `finalize_recommendation` 用于定稿和更新记忆

这条分支重点做了上下文压缩和工具调用治理：

- browse 结果会折叠，不会把完整 tag 列表长期带进后续 prompt。
- `keep_tags` 作为轻量保留信号，只在 browse 后紧接着的下一次工具调用里使用。
- search 结果做了可见候选上限控制，避免一次塞给模型太多题。
- 多 lane 搜索改成更公平的分配策略，避免大 lane 抢光展示名额。
- tag 搜索支持末端关键词匹配，比如 `factor`、`manipulation` 这类词可以直接命中末端节点。
- 模型如果漏写 `keep_tags`，系统也不会崩，只会保留可用的近期 tag 并继续跑。

### Tag 浏览策略

`browse_taxonomy_batch` 的作用不只是“列出所有可能 tag”，而是帮助模型逐步收敛。

这一版的行为更接近真实搜索：

- 如果能直接命中具体可分配 tag，就优先保留这些 tag。
- 只有在 tag 不够具体、为空、或者明显过宽时，才继续向下探索。
- query 可以匹配节点末端内容，减少“搜得到但看不到”的情况。
- 结果返回里会附带简短命中的关键词提示，帮助模型判断为什么这个 tag 被选中。

这让模型在 browse 阶段不必记住大量中间 tag，只需要把真正有用的少数 tag 带到下一步。

### 多 Lane 搜索

`practice_search_batch` 的目标是给模型一个可比较、可决策的候选池，而不是让一个 lane 吃掉全部结果。

现在的策略是：

- 单次可见候选总量仍然受 `2 * questionCount` 限制。
- 先按 lane 分别收集候选，再做公平分配。
- 每个非空 lane 都能先拿到保底展示，通常至少 1 道，条件允许时最多 2 道。
- 剩余名额再按 lane 轮询补齐。
- 如果不同 lane 有重复题，会继续往该 lane 后面找唯一候选，不会因为重复导致小 lane 被挤掉。

这比简单的全局 top-N 更适合“多假设并行搜索”的推荐方式。

### 数学内容与导入链路

数学内容渲染改成了统一的可复用组件，题目页、摘要页、复盘页、编辑页都尽量走同一套展示逻辑。

导入链路也做了增强：

- batch JSON 导入能接收更丰富的题目结构。
- LaTeX 修复能力更强，能处理更脏的表达式。
- package import 和预览路径能保留更多结构化题目信息。
- 题目答案、选项、摘要和富文本在不同页面之间的展示口径更统一。

这部分的目标不是“做更多样式”，而是让内容链路少丢字段、少出错、少出现同一题在不同页面长得不一样。

### 管理与复盘

管理后台补了批量审核和题目编辑能力，便于处理导入后的题目。

这让以下操作更顺手：

- 批量查看和处理待审题目。
- 修改答案相关字段时保持展示链路稳定。
- 维持发布、审题、编辑之间的一致性。

复盘页也更贴近教学场景：

- 给学生看的只是简短反馈。
- 下一轮目标会留在内部上下文里，不直接暴露。
- 学生可以在输入框里补充自己的想法，系统会把这些想法和内部目标一起用于下一轮。

## 模块说明

### `src/lib/practice/agent-loop.ts`

这是推荐 agent 的核心编排层。

它负责：

- 组装 system prompt 和用户上下文。
- 决定本轮可以调用哪些工具。
- 接收工具返回，更新临时 tag 状态和候选池。
- 在合适的时机把 browse 历史折叠掉，减少后续 token 消耗。
- 在 finalize 阶段生成下一轮可复用的 compact tagContext。

### `src/lib/practice/tools.ts`

这是所有 practice 工具的实现层。

它负责：

- taxonomy browse。
- question search。
- 候选题格式化输出。
- 搜索结果公平分配。
- 多 lane 结果去重和截断。

这一层是这条分支 token 优化的主要落点之一。

### `src/components/practice/practice-agent-client.tsx`

这是练习页的主要前端。

它负责：

- 显示推荐、提示、提交、复盘。
- 展示思考中的实时状态和耗时。
- 显示更清晰的正确/错误标记。
- 在复盘后只提供学生补充输入，不暴露下一轮内部目标。

### `src/components/math-content.tsx`

这是数学和富文本展示的统一入口。

它负责把题干、选项、答案、反馈、解题说明这些内容用一致的规则渲染出来，避免不同页面出现不同的数学显示风格。

## 数据流

练习一轮的完整数据流大致是：

1. 前端发起推荐请求，带上当前 goal、sessionMemory、tagContext、已完成题号。
2. 后端创建 recommendation agent，上下文先被压缩成短 prompt。
3. agent 先 browse taxonomy，再根据保留 tag 调 search。
4. search 返回候选题，agent 从中挑选最终题目。
5. 前端展示题目并允许单题提示。
6. 用户提交后，后端批改并生成复盘。
7. 复盘会写入更短的 sessionMemory，并作为下一轮的基础上下文。

这条链路的重点是把“长历史”切成“可复用摘要”，而不是把所有中间过程一直带着跑。

## 风险控制

这条分支对几类风险做了显式约束：

- browse 搜索结果不会无止境地累积到后续上下文。
- `keep_tags` 只在正确时机起作用，漏写或乱写都不会把流程弄死。
- 多 lane 搜索不会因为大 lane 结果多就完全吞掉其他 lane。
- 复盘只给学生可读的简短信息，避免把下一轮策略直接暴露出去。
- 数学内容渲染和导入修复尽量走统一组件，减少页面间分叉。
