## RLS Model

Classroom RLS:

- Teachers/admins can create classrooms inside organizations where they are active staff.
- Teachers/co-teachers/admins can manage classrooms they own or manage.
- Students can read classrooms only after active membership exists.
- Students cannot directly insert arbitrary classroom memberships.
- Anonymous users cannot list classrooms, classroom members, or join codes.

Roster/profile RLS:

- Teachers can read profile rows for active roster members of classrooms they manage.
- Students still cannot enumerate unrelated users.

## Join-Code Behavior

Join codes are generated by the server action when a teacher creates a classroom.

Storage behavior:

- Raw join code is not stored in the database.
- Database stores only a normalized SHA-256 hash and a short hint.
- The full join code is shown once on the classroom detail page after creation.

Known MVP limitation:

- Join-code rotation/regeneration is not implemented in this slice.

## Student Join Flow Result

Implemented:

1. Student opens `/student/classrooms/join`.
2. Student enters teacher-provided join code.
3. App calls `join_classroom_by_code`.
4. RPC validates active student account, organization membership, active code, and active classroom.
5. Student membership becomes active.
6. Student sees joined classroom under `/student/classrooms`.

Automated verification passed after disposable student bootstrap.

Verified by `scripts/classroom-foundation-smoke.mjs`:

- teacher/admin creates a smoke classroom
- hashed join code is created
- student cannot see the classroom before joining
- student joins by code through `join_classroom_by_code`
- student can see the joined classroom
- teacher/admin roster shows the joined student
- anonymous access cannot read the classroom
- smoke-generated records are scoped and cleaned up by revoking the join code, removing the student membership, and archiving the smoke classroom
