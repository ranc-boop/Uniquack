# PDF50-2 Worker Checkpoint and Fencing Design

## Audit status

This document records the source audit completed before runtime changes for
PDF50-2. It covers the durable `ai_provider_jobs` queue as it exists through
canonical migration 0050. No hosted database, Provider, or storage operation
was performed for this audit.

## Current execution contract

### Claim and lease

`public.claim_ai_provider_jobs` (0033, corrected by 0034) uses a locked
candidate selection and writes `lease_owner`, `lease_acquired_at`,
`lease_expires_at`, `execution_attempt_count`, and `status = leased`. It is
service-role executable only. The current limits are global active `3`,
organization active `1`, PDF active `1`, user outstanding `5`, organization
outstanding `12`, and internal route invocation `2`.

The internal `POST /api/internal/ai-jobs/run` route validates the private
`x-ai-jobs-internal-token`, accepts no body, and calls
`runDurableAIProviderJobs({ limit: 2 })`.

### Heartbeat and completion

The worker calls `heartbeat_ai_provider_job(job_id, lease_owner, 900)` before
processing and once per minute. The current heartbeat and finish RPCs compare
the worker string and lease expiration, but they do not carry an immutable
lease-generation token. `finish_ai_provider_job` writes safe terminal or retry
state when the same owner still has an unexpired lease.

### PDF execution and persistence

For `ai_pdf_extract`, the worker validates the Bank, creator, source asset,
and provider route, then updates the import batch to `validating`. It downloads
the private source and calls `runWithAIProviderRoute`, which calls
`processAIPdfImport`.

`processAIPdfImport` currently combines:

1. source-page and preanalysis validation;
2. provider profile load and provider invocation;
3. extraction-response normalization;
4. import JSON construction;
5. Review Draft/question persistence through the existing import boundary;
6. cropped asset attachment;
7. import-batch finalization and coverage/boundary-plan generation.

The current logical job idempotency key prevents duplicate *enqueue* for an
import retry generation. The import service also has its own existing draft
and source-lineage safeguards, but the queue has no durable provider-result
checkpoint or queue-level persisted-output lineage.

### Retry and failure

The worker classifies provider failures, records safe batch progress, and
finishes the queue job as `retry_wait` or `failed`. Retry delay is bounded and
jittered. A successful worker records only safe aggregate telemetry and marks
the job `completed` after the import service returns.

## Current failure windows

| Window | Current outcome | Why it is insufficient |
| --- | --- | --- |
| Death after claim | Lease eventually expires. | No durable stage proves whether source validation started. |
| Death after source validation | A later worker repeats validation. | Safe but unobservable and not stage-idempotent. |
| Provider success before import persistence | The provider can be called again. | Result is not durably available for recovery. |
| Persistence succeeds before queue finish | A later worker can re-enter the service. | Existing import safeguards help, but no queue-level proof says persistence completed. |
| Lease expires while old worker runs | A new owner can proceed after expiry. | The old owner has no immutable fence preventing late writes outside the queue RPCs. |
| Duplicate scheduler wake-up | Locked claim normally avoids duplicate active claims. | There is no stage replay/no-op contract or duplicate-output ledger. |

Direct stale/duplicate write points are the import-batch update in
`claimAIPdfBatchResource`, all batch-progress writes inside the PDF import
service, Review Draft persistence, crop attachment, provider failure recording,
and terminal queue completion. Only heartbeat and finish presently compare the
lease owner; neither has an immutable fencing token.

## Canonical target contract

PDF50-2 introduces the smallest durable stage set for PDF jobs:

`claimed -> source_validated -> provider_request_started ->
provider_result_checkpointed -> normalized -> drafts_persisted -> completed`

Every stage mutation will require the active immutable fence token generated by
the claim. Queue-facing metadata remains bounded: stage name/version, lease
generation, checkpoint version/time, recovery classification, and safe
persisted-output lineage. The provider result itself will be stored only in a
private, service-role-only checkpoint record and only in the normalized
recovery envelope needed to avoid a repeat Provider call. It must never be
returned through requester job status, logs, or telemetry.

The forward migration will add compare-and-set RPCs for heartbeat, stage,
provider-result, persistence, finish, retry, and release transitions. A stale
fence returns the bounded `STALE_FENCE_REJECTED` outcome without changing the
job, batch, or drafts.

The worker will separate provider extraction from draft persistence for
checkpoint-enabled PDF jobs. A recovery worker reuses a compatible protected
result checkpoint; corrupt, incomplete, expired, or incompatible checkpoints
enter a bounded recovery classification and never silently become draft data.
Draft persistence will receive a deterministic source lineage key based on the
source asset, parser/output-contract version, logical item identity, and
checkpoint version, never a visible question number.

## Scope and invariants

- Existing concurrency, admission, routing, Bank scope, Review Draft gate, and
  internal worker route contracts stay unchanged.
- No provider selection, real Provider, hosted Supabase, Vertex, Vercel Queue,
  or assignment/publication behavior is introduced.
- Checkpoint mutations are service-role-only; requester-facing status remains
  safe aggregate metadata.
- Staged persistence cannot auto-publish, create Assignments, overwrite an
  approved question, or reveal source content.
- PDF50-2 source validation uses deterministic fake-provider/local simulations
  only. The migration is not applied in this task.
